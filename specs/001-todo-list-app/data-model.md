# Data Model: To-Do List Application

## Entities

### User

- `userId` (string, UUID or MongoDB ObjectId)
- `username` (string, required)
- `email` (string, required, unique)
- `passwordHash` (string, required)
- `createdAt` (datetime, required)
- `updatedAt` (datetime, optional)

### Task

- `taskId` (string, UUID or MongoDB ObjectId)
- `userId` (string, required, references User)
- `name` (string, required)
- `description` (string, optional)
- `status` (string, required, enum: `pending`, `completed`)
- `createdAt` (datetime, required)
- `updatedAt` (datetime, required)
- `dueDate` (datetime, optional)

## Relationships

- One `User` has many `Task` documents.
- Each `Task` belongs to exactly one `User`.

## Validation Rules

- `username`: required, non-empty, reasonable length (e.g., 3-50 characters).
- `email`: required, valid email format, unique across users.
- `passwordHash`: required; passwords are hashed before storage.
- `name`: required, non-empty, reasonable length (e.g., 1-120 characters).
- `status`: required, must be either `pending` or `completed`.
- `taskId` and `userId` should be generated by the persistence layer and never user-supplied.

## State Transitions

- `pending` → `completed`: when the user marks a task done.
- `completed` → `pending`: when the user re-opens a task.
